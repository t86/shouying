# 收银系统 Flutter 跨平台全量迁移设计

## 1. 背景

现有客户端是 Vue 2 + Vuex 应用，承载点单、收银、预订、会员、存取酒、排队、ERP、BMS、报表和设备管理等业务。静态盘点时，`src` 下约有 584 个 Vue 文件、173 条路由和 67 个 API 模块；权限判断分散在路由、Vuex、Mixin、组件和页面方法中。项目同时依赖 HTTP、WebSocket、扫码、打印、上传下载、Excel 和二维码等能力。

本次迁移是独立客户端试验，现有后端不配合改造。Flutter 客户端必须兼容既有 HTTP、鉴权、WebSocket、错误码和数据语义，不新增后端前置条件。

## 2. 目标

构建一套共享 Flutter 业务内核和三个平台应用：

- Windows：门店电脑主收银终端，最终全量覆盖现有系统功能。
- Flutter Web：浏览器入口，最终全量覆盖现有业务功能；浏览器受限的硬件能力允许采用明确的降级实现。
- Android：移动辅助端，只开放适合移动操作且在迁移台账中明确批准的能力。

业务功能、权限判断、接口参数和服务端最终结果必须与现有 Vue 系统一致。界面不要求像素级复刻，可以针对桌面、浏览器和移动端重新设计交互。

迁移期间 Vue 继续运行，作为功能对照和安全回退入口。

## 3. 已确认约束

- 现有后端接口、鉴权和 WebSocket 协议原则上不变。
- 不依赖后端团队提供新接口、幂等能力、离线同步或协议升级。
- Windows 是正式收银平台；门店电脑只要求支持 Windows。
- Flutter Web 和 Windows 需要全量业务覆盖。
- Android 不要求全量覆盖，平台能力以迁移台账为准；未登记的功能默认不在 Android 范围内。
- 系统不支持离线业务。断网后禁止新增、修改、支付、退款及库存写入。
- 扫码枪和小票打印机由各门店自行采购，客户端只承诺兼容公开标准，不承诺兼容任意厂商私有协议。
- 扫码枪采购标准为支持 USB HID 键盘模式。
- 小票打印机采购标准为支持 Windows 打印驱动或 ESC/POS，连接方式可为 USB、LAN 或蓝牙。
- 钱箱不在范围内。

## 4. 不在本设计范围内

- 修改后端业务逻辑或接口契约。
- 新增完整离线开单、离线支付或联网后冲突合并。
- 为每个打印机、扫码枪品牌编写专用适配。
- 让三个平台强制复用同一套页面布局。
- 在未通过可行性关卡前一次性重写全部页面。
- 在迁移完成后继续以 WebView 作为正式业务实现。

WebView 可以在迁移期作为临时回退入口，但不得成为最终架构的一部分。

## 5. 方案选择

### 5.1 推荐方案：共享业务内核、平台化界面和能力适配

三个平台共享协议、领域模型、权限、业务用例和实时同步；Windows/Web 使用桌面交互，Android 使用移动交互；扫码、打印、文件和安全存储通过平台接口适配。

该方案能够同时保证业务一致性和平台体验，是本设计采用的方案。

### 5.2 未采用：三个独立 Flutter 应用

各端可以独立演进，但业务规则、权限和协议实现会逐渐分叉，难以证明功能等价。

### 5.3 未采用：一套响应式页面覆盖所有平台

初期代码较少，但桌面收银的高密度键鼠操作与移动端触控差异过大，最终会产生大量平台条件和难以维护的布局分支。

### 5.4 未采用：WebView 套壳并逐页替换

适合短期演示，但会引入路由、鉴权、扫码、打印和状态同步的双重桥接，不适合作为全量迁移主路线。

## 6. 平台定位

| 平台 | 定位 | 功能范围 | 硬件范围 |
| --- | --- | --- | --- |
| Windows | 门店主收银终端 | 现有业务全量覆盖 | HID 扫码；Windows 打印队列；USB/LAN/蓝牙 ESC/POS |
| Flutter Web | 浏览器管理与应急业务入口 | 现有业务全量覆盖 | 浏览器/系统打印；上传下载；不承诺静默 ESC/POS |
| Android | 移动辅助终端 | 迁移台账逐项批准 | 相机/HID 扫码；USB/LAN/蓝牙 ESC/POS |
| Vue Web | 迁移期旧系统 | 保持现状 | 对照与回退 |

最终功能可用性按照以下交集计算：

```text
最终可用功能
= 后端返回权限
∩ 当前平台的批准范围
∩ 当前终端可用设备能力
```

Android 未开放的功能必须标记为“不在范围”，不能标记为“遗漏”或通过修改原有权限定义隐藏。

## 7. 工程结构

在现有仓库新增独立 Flutter 工作区，Vue 工程保持原有目录和构建流程：

```text
flutter_workspace/
├── apps/
│   ├── windows_app/
│   ├── web_app/
│   └── android_app/
├── packages/
│   ├── protocol/
│   ├── realtime_sync/
│   ├── permissions/
│   ├── session/
│   ├── design_system/
│   ├── device_bridge/
│   └── features/
│       ├── order/
│       ├── cashier/
│       ├── booking/
│       ├── member/
│       ├── wine/
│       ├── queue/
│       ├── erp/
│       ├── bms/
│       └── reports/
└── integration_tests/
```

三个 `app` 是薄壳，只负责窗口、平台启动、路由装配、功能注册、布局入口和平台能力绑定。

### 7.1 业务模块结构

```text
feature/order/
├── domain/
│   ├── entities/
│   ├── repository_interfaces/
│   └── use_cases/
├── data/
│   ├── dto/
│   ├── mappers/
│   └── repositories/
├── application/
│   └── view_models/
└── presentation/
    ├── desktop/
    ├── mobile/
    └── shared/
```

同一个业务用例只能实现一次。不同平台可以采用不同的页面，但必须调用相同用例、权限决策和 Repository 接口。

### 7.2 依赖方向

```text
apps
  ↓
presentation
  ↓
application / ViewModel
  ↓
domain / UseCase
  ↓
repository interface
  ↑
data implementation
  ↑
HTTP / WebSocket / platform service
```

依赖约束：

- View 只负责展示、输入、布局和简单路由，不包含金额、权限或订单状态规则。
- ViewModel 负责界面状态和流程编排，不解析原始接口字段。
- 跨页面、跨平台或复杂业务逻辑放入领域用例。
- Repository 是业务数据的唯一来源。
- API DTO 只存在于数据层，转换成领域模型后才能进入上层。
- Repository 之间不相互依赖；跨 Repository 组合放在用例或 ViewModel。
- 业务模块不能引用其他模块的 `presentation` 或内部数据实现。
- 功能代码不能直接判断 `Platform.isWindows` 或 `kIsWeb`。
- 禁止建立包含全部业务数据的巨大、全局可变状态仓库。

架构采用 MVVM + 领域用例。状态管理和依赖装配默认使用 Riverpod，但 Riverpod 类型不能进入领域公共接口。

## 8. 协议兼容层

Flutter 作为协议兼容客户端，完整复刻：

- 基础地址和环境切换；
- HTTP 方法、路径、参数名称和序列化方式；
- `tk`、`stk`、`tt` 等请求头；
- 登录、退出、Token 失效语义；
- 12 秒超时及既有重复请求拦截行为；
- 文件上传、二进制下载、Excel 和图片请求；
- 服务端业务错误和异常响应结构；
- WebSocket `/sync`、鉴权、心跳、重连、全量刷新和增量补偿；
- `last_sync_time` 等同步游标及时间语义；
- 门店、用户、营业日、卡台、商品和配置的状态更新关系。

协议层内部区分：

- Raw DTO：与后端字段一一对应，允许保留后端命名。
- Mapper：处理数字字符串、空字符串、缺失字段和数组压缩结构。
- Domain Model：使用稳定、可读的客户端业务模型。
- Repository：向上层提供统一的业务数据和状态流。

未知新增字段默认忽略；关键必需字段缺失或类型无法安全转换时返回 `ProtocolFailure`。支付、退款和库存写入遇到协议异常时必须失败关闭，不能继续猜测执行。

## 9. 权限模型

权限不只是菜单权限，还包括：

- 系统角色；
- 当前岗位和身份；
- 按钮及子权限；
- 区域范围；
- 商品或分类范围；
- 赠送类型；
- 优惠、赠送、退款等额度限量；
- 二次授权；
- 特殊角色兼容逻辑。

统一权限引擎输入用户、门店、岗位、业务对象、平台和设备能力，输出：

```text
PermissionDecision
├── allowed
├── reason
├── requiredAuthorization
└── effectiveScope
```

页面可见性、按钮可用性和提交前校验使用同一权限引擎。页面隐藏只是交互控制，业务用例执行前必须再次校验；服务端仍然是最终权限裁决者。

## 10. 设备能力层

设备能力采用平台接口与平台实现分离：

```text
device_bridge/
├── device_bridge_platform_interface/
├── device_bridge_windows/
├── device_bridge_android/
└── device_bridge_web/
```

业务层只依赖：

```text
ScannerService
PrinterService
FileExportService
CredentialStore
```

### 10.1 扫码

- Windows 主路径为 USB HID 键盘模拟扫码枪。
- Android 支持 HID，并以相机扫码作为无外设兜底。
- 扫码服务处理全局输入缓冲、结束符、最大间隔、防抖、焦点无关接收和手工输入冲突。
- 采购文档明确要求扫码枪支持 HID 键盘模式，默认以回车结束条码。

### 10.2 打印

Windows 打印优先级：

1. 已安装 Windows 驱动的系统打印队列。
2. LAN 打印机通过 IP 和端口发送 ESC/POS。
3. 可识别的 USB ESC/POS 设备。
4. 蓝牙打印作为补充。

Android 支持 USB、LAN 和蓝牙 ESC/POS。Flutter Web 使用浏览器或系统打印，不承诺静默打印、自动切纸或直接控制任意 USB 打印机。

打印模型是结构化小票，不复用 Vue HTML：

- 58mm/80mm 纸宽；
- 中文、商品明细、金额、时间；
- 二维码；
- 切纸能力；
- 测试小票；
- 打印任务状态；
- 失败重试和补打。

支付成功和打印成功是两个独立状态。打印失败不得回滚支付，必须保留可补打记录。

## 11. 在线状态与数据一致性

系统不提供离线业务，统一定义：

- `online`：HTTP 和实时同步健康，可以操作。
- `blocked`：网络、鉴权或关键同步不可用，所有写操作禁止。
- `reconciling`：连接刚恢复，正在校验会话、补偿同步并刷新业务对象。

恢复流程：

```text
网络恢复
→ 校验登录状态
→ 恢复 WebSocket
→ 执行增量补偿
→ 重新查询当前业务对象
→ 核对未完成操作
→ 确认服务端最终状态
→ 切换为 online
```

断网时可以在内存中保留尚未提交的表单，但不能创建订单、修改订单、收款、退款或修改库存。应用退出后不保证恢复未提交表单。

### 11.1 支付状态机

```text
待支付
→ 提交中
→ 服务端处理中
→ 已成功 / 已失败 / 结果未知
```

请求超时或连接中断只能进入“结果未知”，不能直接判定失败，也不能自动重发支付。恢复网络后先查询服务端最终状态。只有服务端明确确认原支付失败后，才允许重新发起。

## 12. 迁移台账

完整性保障使用三类台账。

### 12.1 功能台账

颗粒度是用户可执行的业务能力，而不是页面。订单详情需要拆分为查看、加菜、退菜、赠送、修改数量、换台、结账和补打等能力。

每项记录：

- 功能编号；
- 业务域；
- Vue 路由、组件、方法、弹窗和快捷键来源；
- 前置条件；
- 用户输入；
- 正常结果；
- 异常结果；
- 权限规则；
- 接口和状态依赖；
- Windows/Web/Android 范围；
- Flutter 实现位置；
- 自动化测试；
- 人工验收证据；
- 当前迁移状态。

示例：

| 功能编号 | 能力 | Windows | Web | Android | 状态 |
| --- | --- | --- | --- | --- | --- |
| `ORDER-001` | 查看卡台 | 必须 | 必须 | 台账批准后开放 | 已发现 |
| `CASHIER-PAY-003` | 扫码收款 | 必须 | 必须，硬件可降级 | 默认不开放 | 已发现 |
| `PRINT-002` | 补打小票 | 必须 | 浏览器打印 | 台账批准后开放 | 已发现 |

### 12.2 协议台账

记录每个 HTTP 和 WebSocket 行为：路径、方法、请求头、参数、字段类型、空值、响应、错误、超时、重试、调用者、状态影响和风险等级。

### 12.3 权限台账

把角色、岗位、区域、商品、额度和二次授权转换为可执行的权限真值表，作为三端统一测试输入。

### 12.4 盘点方法

采用三层盘点：

1. 静态提取路由、页面、API、Vuex、本地存储、WebSocket、权限、按钮、弹窗、快捷键、打印和导入导出。
2. 使用测试账号运行旧系统，采集脱敏的请求、响应、实时消息、截图和不同角色可见内容。
3. 由熟悉门店业务的人员走查真实工作流，确认隐含规则和废弃功能。

功能同时通过静态提取、运行时采集和业务复核后，才能从“已发现”进入“已定义”。

### 12.5 状态流转

```text
已发现
→ 已定义
→ 已实现
→ 协议一致
→ 权限一致
→ 异常流程一致
→ 真机/浏览器通过
→ 业务验收
```

页面能打开不等于完成。每项完成能力必须关联旧代码来源、Flutter 实现、契约测试、权限测试、正常/异常用例及验收证据。

## 13. 分阶段迁移

### 阶段 0：冻结基线

建立功能、接口、权限、状态和设备台账，采集脱敏协议样本、角色真值和关键流程证据。Vue 后续新增或修改关键能力时，CI 必须标记受影响的 Flutter 功能编号。

完成门槛：所有路由、API 和权限来源至少进入“已发现”；第一批收银闭环进入“已定义”。

### 阶段 1：跨平台技术验证

建立最小工作区并验证：

- 三端构建和发布；
- HTTP 和鉴权兼容；
- 登录、退出和 Token 失效；
- WebSocket 同步、重连和增量补偿；
- 权限引擎；
- Windows HID 扫码及真实打印；
- Flutter Web 路由、文件、浏览器打印和同源部署；
- Android 相机/HID 扫码及 ESC/POS 打印。

完成门槛：三端使用相同测试账号登录并产生等价请求；权限决策一致；Windows 完成真实扫码和测试小票。

### 阶段 2：Windows 第一个收银闭环

```text
登录
→ 选择终端身份
→ 获取门店和权限
→ 检查营业状态
→ 展示卡台
→ 创建或进入订单
→ 选择/扫描商品
→ 修改订单
→ 发起收款
→ 确认服务端最终状态
→ 打印或补打小票
```

该闭环优先验证权限、实时同步、订单写入、支付状态和硬件。

### 阶段 3：扩展至 Web 和 Android

Windows 收银闭环稳定后，Flutter Web 复用相同领域逻辑和桌面组件；Android 只装配迁移台账批准的移动能力。

### 阶段 4：按领域迁移

推荐顺序：

1. 登录、会话、门店、权限和营业状态。
2. 卡台、点单、收银、支付、退款和打印。
3. 预订和排队。
4. 会员及会员支付。
5. 存酒和取酒。
6. 商品、库存、出入库和 ERP。
7. BMS 配置、岗位、角色和设备。
8. 报表、Excel 导入导出和低频管理功能。
9. 超级管理员及遗留边缘功能。

迁移单位为包含协议、模型、权限、用例、页面、异常、测试和验收的纵向业务切片，不按页面批量翻译。

### 阶段 5：灰度替换

```text
开发环境
→ 内部测试终端
→ 测试门店
→ 单个真实门店并行运行
→ 少量门店灰度
→ 分批扩大
→ Windows/Web 全量切换
→ Vue 进入只维护状态
```

试点期间 Vue 是回退入口，但同一笔订单不能在两个客户端同时编辑。

## 14. 测试策略

### 14.1 协议契约测试

固定输入后比较 Vue 和 Flutter 的 URL、方法、请求头、JSON、空值、数字/字符串类型和响应转换。脱敏真实响应作为回归样本。

### 14.2 权限真值测试

对角色、岗位、区域、商品、额度和授权组合，验证菜单、按钮、字段、提交权限及拒绝原因。

### 14.3 业务用例测试

覆盖金额、订单状态、优惠、赠送、退款、营业日和跨 Repository 组合规则。

### 14.4 跨平台集成测试

同一业务用例在 Windows、Web 和 Android 范围内运行。设备测试使用真实 Windows 终端、HID 扫码枪及至少一台 58mm 或 80mm 打印机。

### 14.5 Vue/Flutter 对照测试

在隔离测试门店使用相同账号、前置数据和操作，对比请求、权限、服务端最终状态和用户可见结果。支付等写操作不得在生产数据上重复发送。

UI 可以重新设计，不比较像素；必须比较输入项、默认值、校验、权限、金额、状态、可执行操作以及成功/失败后的业务结果。

## 15. 错误处理

底层异常统一映射为类型化失败：

| 类型 | 行为 |
| --- | --- |
| 网络不可用 | 进入 `blocked`，禁止写操作 |
| Token 失效 | 清理会话并返回登录 |
| 后端业务拒绝 | 显示可操作的业务原因 |
| 协议异常 | 停止当前操作并记录契约差异 |
| WebSocket 中断 | 阻止依赖实时状态的写操作 |
| 支付结果未知 | 查询最终状态，禁止自动重付 |
| 打印失败 | 保留打印任务并允许补打 |
| 设备不兼容 | 显示标准要求和设备测试入口 |

只有明确幂等的查询请求可以自动重试。下单、支付、退款和库存写入不能使用通用自动重试。

## 16. Flutter Web 专项设计

现有请求包含自定义请求头，浏览器可能触发 CORS 预检。由于后端不配合，Flutter Web 必须与现有服务保持同源。迁移期建议：

```text
/shouyin/       现有 Vue
/shouyin-v2/    Flutter Web
/api/...        现有接口
```

第一期使用默认 Web 构建，不启用需要额外 COOP/COEP 响应头的 Wasm 多线程部署。

专项验收包括：

- 刷新后恢复路由；
- 浏览器前进和后退；
- 多标签页会话一致性；
- 高密度表格、复制和键盘操作；
- 中文输入法；
- Excel 上传下载；
- 浏览器打印与分页；
- 缓存导致的新旧版本混用；
- 首屏、列表滚动和大表格性能。

## 17. 工程与依赖策略

建议基础栈：

- Riverpod：状态和依赖装配。
- `go_router`：跨平台 URL、深链接、权限重定向和嵌套路由。
- Dio：封装现有 HTTP 协议和拦截器。
- 代码生成 JSON DTO：保证字段映射可测试。
- `flutter_test` 与 `integration_test`：单元、组件及集成测试。

依赖要求：

- Flutter SDK 和所有包版本锁定在仓库。
- 禁止业务层暴露第三方插件类型。
- 插件必须有明确许可证和目标平台支持，或由内部平台适配层隔离。
- 依赖升级作为独立任务执行，并重新运行三端构建与兼容测试。
- 不引入离线业务数据库。

## 18. 分支和协作

- 前期使用短期 `feature/flutter-foundation` 分支完成技术验证。
- 可行性通过后，把新增 `flutter_workspace/` 合入 `dev`。
- 后续使用短期能力分支，例如 `feature/flutter-CASHIER-PAY-003`。
- 不维护长期不合并的 `flutter` 分支。
- 每个 PR 关联一组相关功能编号，并同步更新台账、测试和平台范围。
- Vue 中已迁移能力发生变化时，必须评估并更新 Flutter 差异状态。
- Flutter 初期不修改现有 Vue 构建和发布流程。

## 19. CI 与发布

每次 PR 执行：

```text
格式检查
→ 静态分析
→ 依赖边界检查
→ 单元测试
→ 协议契约测试
→ 权限真值测试
→ Widget 测试
→ Web Release 构建
→ Windows Release 构建
→ Android Release 构建
```

Windows 构建运行在 Windows 构建机。Web、Windows 和 Android 独立生成版本化产物，不能以一个平台构建成功推断另一个平台可发布。

夜间或发布前执行三端集成、Vue/Flutter 对照、WebSocket 恢复、支付未知状态恢复、设备测试、性能测试和迁移覆盖率报告。

Windows 初期使用签名安装包或门店现有软件分发方式。自动更新是后续独立能力，不作为首个闭环的前置条件。

## 20. 可观测性和安全

Windows 收银端提供可导出的诊断包，包含：

- 应用版本和构建号；
- 平台及设备信息；
- 功能编号；
- 脱敏接口耗时和状态码；
- WebSocket 状态变化；
- 支付状态迁移；
- 打印任务状态；
- 脱敏异常堆栈；
- 最近一段环形日志。

日志禁止包含 `tk`、`stk`、密码、完整手机号、银行卡信息、付款码及完整敏感请求响应。

Token 存储通过平台接口实现：Windows 使用系统凭据能力，Android 使用系统安全存储，Web 遵循浏览器同源安全边界。任何平台都不能在调试日志或诊断包中输出 Token。

## 21. 防止协议漂移

- 每个 DTO 保留脱敏响应样本。
- 契约快照记录字段类型、关键必填项和特殊空值。
- 未知新增字段忽略，关键字段缺失产生 `ProtocolFailure`。
- Vue API、WebSocket、权限和关键业务文件变化时，CI 输出受影响功能编号。
- 每次 Flutter 发布生成协议基线摘要。
- 无法解析的 WebSocket 消息记录脱敏摘要和消息编号。
- 关键协议异常时禁止支付、退款或修改业务状态。

## 22. 可行性关卡

### 关卡 A：协议可行

三端无需后端修改即可登录、调用接口和连接 WebSocket，协议与权限对照通过。

### 关卡 B：Windows 收银可行

真实电脑完成扫码、下单、支付状态恢复、打印和补打。

### 关卡 C：Flutter Web 可行

高密度表格、浏览器路由、上传下载、打印、中文输入和首屏性能达到业务可用标准，且无需后端或网关配合解决跨域。

三个关卡全部通过后才能进入全量迁移。如果关卡 C 失败，应重新评估 Web 表现层技术路线；共享协议、领域规则和 Windows/Android 成果仍然保留。

## 23. Vue 退出门槛

某个业务域只有同时满足以下条件，才能由 Flutter 替换 Vue：

- Windows 和 Web 范围内的功能台账 100% 关闭；
- Android 已批准范围全部关闭；
- 协议差异为零；
- 权限差异为零；
- 正常和异常用例通过；
- 支付结果未知可以恢复；
- 扫码和打印通过真实 Windows 设备验证；
- 不存在阻断收银的已知缺陷；
- 业务人员完成验收；
- 已验证回退到 Vue 的流程。

只有 Windows/Web 全量台账关闭后，整个 Vue 系统才进入只维护状态。
